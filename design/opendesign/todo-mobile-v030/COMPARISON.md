# COMPARISON — 三套概念的横向评估与推荐

> 评估对象：`concept-a/`（稳定骨架）、`concept-b/`（分桶清单）、`concept-c/`（时间轴优先）。
> 评估基准：`AUDIT.md` 的五个根因，以及冻结的 D Final 视觉契约与 `docs/CORE_UX_SPEC.md` 的信息架构。
> 三套方案共用同一套视觉语言、同一套色板、同一套触控标准，**只在信息架构与交互模型上分歧**。

---

## 一、三套方案的一句话定义

| | 概念 | 组织轴 | 未安排怎么处理 | 日期怎么处理 | 创建入口 |
|---|---|---|---|---|---|
| **A** | 稳定骨架 | 固定视图槽位（今天 / 未安排 / 全部）+ 日期带 | 与今天、全部并列的一个**视图** | 周一~周日日期带 + 「全部日期」格 | 右上角 `＋ 待办` → 底部 Quick Create |
| **B** | 分桶清单 | 数据推导的紧急度分桶 + 三个可滑动标签 | 不设专门视图，作为**逾期桶/无截止桶**自然出现 | 顶栏「日期」胶囊 → 底部选择面板 | 右上角 `＋ 待办` → 全屏 Quick Create |
| **C** | 时间轴优先 | TaskAllocation 计划执行时段 | 常驻**可拖动托盘**，拖到轴上即完成安排 | 左右切日的小时时间轴 | 右上角 `＋ 待办` 或**点时间轴空格** → 底部 Quick Create |

## 二、六个维度逐项打分与判断

打分只用于表达相对位置，不作为加权总分——**下面每个维度都给出明确的胜负判断，不平均**。

### 1. 好看

**A ≈ B > C**

三套都遵守同一套契约：钴蓝 `#2457D6`、画布 `#F5F6F8`、扁平分组行 + 1px 分隔、无渐变、无装饰阴影、无卡片嵌套。所以"好看"的分差不来自颜色，而来自**密度与呼吸感**。

- **A** 的密度最均衡：日期带提供横向节奏，列表区是干净的扁平行。视线有一条清晰的"顶 → 日期 → 列表"纵向动线。
- **B** 的分桶标题（粘性）给页面增加了第二层结构，滚动时层级感最强，视觉最"有设计感"；但三个标签页 + 三个粘性桶头 + 一个顶栏胶囊，竖向堆了四层横向控件，比 A 略满。
- **C** 的时间轴在"有安排的日子"很好看，在"只有截止待办的日子"会退化成一串 44px 细条 + 大片空白小时格，是三者中视觉落差最大的。

**判断：好看这一项 A 与 B 并列第一，C 第三且落差明显。**

### 2. 好懂

**B > A > C**

这是 B 真正赢的一项，也是我认为 B 值得被记录下来的唯一理由。

- **B** 的"逾期 / 今天 / 明天后 / 无截止"是用户脑子里**本来就有的分类**，不需要学习。一个从未用过 DaySpark 的人打开 B，不需要理解"视图""透镜""槽位"任何一个概念。
- **A** 需要用户先理解"今天 / 未安排 / 全部"是三个**视图**而不是三种数据。这是一个真实的学习成本，只是它和 Todoist / TickTick 一致，多数用户已经从别处学过了。日期带里的「全部日期」格是一个新造物，需要一次理解。
- **C** 需要理解最多：时间轴模式与清单模式是两套心智模型；托盘是一个既不是视图也不是列表的东西；"细条=只有截止，块=有计划执行"是一套需要图例的编码。我在 C 的原型里不得不写了三条注释来解释这三种色块的含义——**需要注释来解释的界面，本身就是这条维度的扣分**。

**判断：好懂 B 第一。A 第二但胜在有成熟产品铺过路。C 第三。**

### 3. 好操作

**A > B > C**

高频操作只有一个：**看到一条待办，标记完成**。次高频：**新建一条待办**。

- **A** 的完成入口在每行左侧 48dp 复选框，拇指自然落点；新建在右上角，单手可及；改日期在顶部日期带，一次点击。三条主路径都在拇指范围内。
- **B** 完成入口同样好，但**改日期需要三步**（点胶囊 → 等底部面板 → 选日期），比 A 的日期带多一步。标签页左右滑动与列表竖向滚动存在手势冲突，实测中容易误切页。
- **C** 完成入口在时间块内，命中区域随时间块高度变化——44px 的细条只有 44dp 高，是三者中唯一**触控目标高度会随数据变化**的方案，直接违反"高频率点击目标必须有稳定触控尺寸"。拖动安排在单手握持下基本不可靠，我在 C 里不得不补一条"选择时段"的兜底路径，等于承认主路径失败。

**判断：好操作 A 第一，且优势明确。C 第三。**

### 4. 功能完整

**A = B = C**（平手，且这是硬约束）

题目要求不得移除：标题、截止时间、重复、计划执行、多 Reminder、多日历、优先级、标签、描述、子任务、附件。三套方案都完整覆盖，且都用了同一种手段：**折叠分组 + 有值自动展开 + 二级页面承载子任务/附件**。

真正的差别在**语义保真度**：

- **C** 对 `dueDate` / `TaskAllocation` 的区分表达得最彻底——它把两者在表单里分成两个独立分组，并在时间轴上用三种视觉状态编码，是最不可能让用户混淆的一套。
- **A** 用「截止」与「计划执行」两个并列胶囊区分，语义清晰但全靠文字。
- **B** 把两者压成一组日期/时间胶囊，语义保真度最低——**这是 B 在功能维度上的实质扣分**，只是因为它没有丢字段，所以仍算"完整"。

**判断：表面平手。语义保真度 C > A > B。这一项决定了 B 不能直接采用。**

### 5. Android 人机工程

**A > B > C**

逐条对照：

| 检查项 | A | B | C |
|---|---|---|---|
| 高频目标 ≥48dp | ✅ 复选框 48、行 60、日期格 52 | ✅ 复选框 48、行 60、标签 48 | ⚠️ 时间块 44~128 不等，**高度随数据浮动** |
| 单手拇指可达 | ✅ 完成在左下、新建在右上 | ✅ 同 A | ⚠️ 托盘在底部（好），但轴上块在中上部（差） |
| 键盘弹起 | ✅ 底部 Sheet 跟随，Safe Area 已留 | ✅ 全屏页，输入框不被遮 | ✅ 同 A |
| 系统字体缩放 1.3× | ✅ 标题 2 行截断，行高自适应 | ✅ 同 A | ⚠️ 时间块文字在缩放后溢出，需额外处理 |
| 360dp 小屏 | ✅ 日期带可横向滚动 | ✅ 标签文字缩短 | ❌ 时间轴在 360dp 下可用宽度不足 300dp |
| 长文本 | ✅ `clamp-2` + 省略号 | ✅ 同 A | ⚠️ 时间块内文字只能单行截断 |
| Safe Area | ✅ 上 52 / 下 28 | ✅ 同 A | ✅ 同 A |

**判断：A 是唯一在全项目录上无 ⚠️ 的方案。**

### 6. 实现复杂度

**A < B < C**

- **A**：一个 `SegmentedButton` + 一个横向 `ListView` + 一个 `BottomSheet` + 折叠分组。全部是标准 Material 3 控件，无需自定义绘制。**预估：可直接落到现有 `TodosView` / `TodosDayView` / `TodosInboxView` / `TodosAllView` 四个既有 view state 上，新增代码集中在呈现层。**
- **B**：需要自绘粘性分桶头 + 三个标签页的 `PageView` 联动 + 数据推导分组的纯函数。分桶规则（逾期 / 今天 / 明天后 / 无截止）需要产品侧确认，是新的业务逻辑而非纯呈现。
- **C**：需要自绘时间轴（小时格、块布局、重叠并列、now line）、拖放手势、托盘、以及与清单模式的双向同步。**这是唯一需要引入自定义布局与手势系统的方案，且拖放在 Flutter 中要处理滚动冲突。**

## 三、明确推荐

# 推荐 Concept A「稳定骨架」

不平均、不和稀泥：**A 在"好操作"和"Android 人机工程"两个与本题最相关的维度上明确第一，在"实现复杂度"上明确最低，在"好看"上与 B 并列第一。它输掉的只有"好懂"一项，而那一项的成本可以用一次 onboarding 和一致的成熟范式消化。**

### 推荐 A 的四个决定性理由

1. **它对 P1 的修复是结构性的，不依赖数据。**
   A 的顶段与日期带是两个**固定槽位**，在四个视图里渲染高度完全一致。抖动的唯一来源从"用户切换了视图"降为"数据本身变了"——后者是正常的。B 声称做到了同样的事，但它的分桶高度随数据变化，页面仍然会跳；C 则连视图切换本身都带着模式切换。

2. **它把 48dp 的预算花在了最重要的控件上。**
   A 的视图段是 42~48dp 的 `SegmentedButton`，日期格 52dp，待办行 60dp。这直接回应了 P2——现状是把最重要的导航交给 36dp 的 Chip，却把 48dp 花在一个按钮上。A 把这个预算重新分配了。

3. **它是三套中唯一不需要用户学习新范式的。**
   Todoist 的视图段 + 日期带、Things 3 的底部 Quick Sheet、TickTick 的折叠分组——A 的每个部件都能在一个成熟产品里找到对应。题目要求"已经被成熟产品解决的问题，优先采用成熟范式"，A 是执行得最彻底的一套。

4. **实现风险最低，且能落在既有架构上。**
   四个既有 view state 可以直接映射到 A 的三个视图，不需要新的业务逻辑、不需要自定义绘制、不需要手势系统。这意味着设计稿到正式实现之间的失真最小。

### 从 B 和 C 带走什么

不采用 ≠ 不借鉴。`final/` 在 A 的骨架上吸收了三处：

- **来自 C：把「计划执行」放在 Quick Create 属性条的第一位**，并在待办行上把 `计划执行` 与 `截止` 分成两个胶囊显示。这用最低成本拿到了 C 最大的语义优势——让用户永远看清"什么时候做"和"最晚什么时候完成"是两件事。
- **来自 C：在编辑页把「安排到时间轴」/「安排执行时间」提为最靠前的一个动作**，让"未安排 → 进入计划"是一条显眼路径，而不是藏在日期字段里。
- **来自 B：它的失败教训**——B 暴露了"标签文案随数据变化"会破坏稳定性，`final/` 因此规定**视图段与日期带的槽位数量、顺序、尺寸在任何数据状态下都不得改变**，只有日期格的选中态和数字徽标可以变。

### 为什么不选 B

B 的"好懂"是真实的，但它为此付出了两个不可接受的代价：**日期/时间胶囊把 `dueDate` 与 `TaskAllocation` 压成了一组字段**，触碰了本题"不可推翻"的语义红线；**粘性分桶头让页面高度随数据变化**，等于没有解决 P1。前者是语义问题，后者是它自己的核心主张。两条都命中，B 只能作为思路留存。

### 为什么不选 C

C 的想法最大胆，也最贴近 DaySpark 独特的 `TaskAllocation` 能力。但它是唯一在**触控目标稳定性**上违反硬约束的方案（时间块高度 44~128dp 浮动），也是唯一在 360dp 小屏上不可用的方案，还是唯一需要自定义布局 + 手势系统 + 滚动冲突处理的方案。**用一个高风险的交互模型去换一个语义清晰的表单分组，代价不对等。** C 的正确用法是作为 DaySpark 后续"日历视图"的独立探索方向，而不是 Todo 主页面的主结构。

## 四、被三套方案共同确认的设计决策

这些不需要再讨论，直接进入 `final/`：

1. **单一创建入口**：右上角 `＋ 待办`，遵循 `docs/CORE_UX_SPEC.md:41`。移除内联 `TodoQuickAdd`。
2. **Quick Create 的标题是绝对视觉中心**：26sp 粗体 + 钴蓝下边框，属性条在标题输入后才出现。
3. **Quick Create → Full Edit 必须携带已输入标题**，绝不清空（P4）。
4. **所有默认值必须文字明示**，绝不静默落 `dueDate = 今天` 或 `calendars.first.id`（P3）。
5. **真渐进披露**：折叠分组 + 有值自动展开 + 二级页面承载子任务/附件，不是只加 Section 标题（P5）。
6. **空状态用列表内的一条插槽**，不用整屏留白填充（P5）。
7. **不新增 FAB、不新增一级导航、不改变今天/日历/待办的一级结构。**
