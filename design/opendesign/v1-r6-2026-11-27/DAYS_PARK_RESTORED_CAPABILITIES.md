## 4. 设计 / 原型必须补出的可见面

1. **待办列表 / 今天**：重复系列行仍是系列行；点完成弹出实例选择器（最近 30 天 + 未来 90 天，30 天分页），选中后只完成该实例；撤销只撤销该实例；已遗漏实例可补完成。
2. **待办详情**：计划执行区必须支持 0..n 行，“添加”可连续新增；每行可改期或取消；取消后保留历史（至少可发现、可解释）；完成待办后晚于完成时刻的计划显示“已失效”且不占时间。
3. **日历空白槽 / 时间槽**：必须同时出现「新建日程」「安排待办」；选择安排待办后选已有待办，保存只出现计划块，截止不变；重复待办先选实例。
4. **提醒区**：多行提醒 + 添加；无截止/无重复开始时相对选项禁用并解释；改变计划后提醒文案不跳参考时间。
5. **旧重复规则**：首次安排/展开时出现一次性确认对话（时区 + 重复起点 + 规则预览）；取消保持原样；确认后才创建实例级计划。
6. **设置 / 小组件**：通知设置只控制系统投递，不删提醒数据；小组件对重复系列不做“替用户选实例”的完成。

## 5. 未能从真实契约确认 / 需要保持谨慎的点

- **计划执行历史的展示粒度**：SPEC 规则 5 明确“用户取消的 Allocation 保留历史……Todo 历史可查看”，但当前 Flutter 详情区只列出 `active` 计划（`execution_schedule_section.dart` 过滤 `state == 'active'`）。因此“历史可查看”是契约要求、不是现状；设计需补一个可发现的历史入口，但具体是折叠区、历史页还是仅“已取消”行，SPEC 未规定。
- **提醒删除/完成分档的 UI 细节**：SPEC 3.5 规则 4 规定 `removed` / `inactive` / `pastDue` 分档及 snooze 保护；这些是通知引擎行为，产品界面只需保证“提醒行保留但不再触发”和“重新给参考时间可恢复”，不必暴露内部档位。
- **计划执行是否在原型内持久化**：产品规格允许原型模拟网络/同步，但不允许把 0..n 退化为“一个当前计划”；原型可用本地状态模拟，但多行、状态与实例绑定必须真实可见。
- **事件重复删除范围**：本轮只纠正待办侧；事件仍保留“仅这一次 / 这一次及以后 / 整个系列”的删除范围，未改其领域语义（SPEC 边缘情况 5 要求删除重复事件明确提示并作用于系列；现有事件实现含 `excludeOccurrence`）。
- **提醒锚点口径**：任务原话中的“计划开始或截止”，在真实契约里应读作**日程开始或待办截止**。SPEC 规则 9 明确“首版 TaskAllocation 不独立支持提醒”，因此计划执行的新增/改期/取消不能创建或改写提醒；相对提醒的时间锚点来自 Event.start 或 Todo.dueDate。原型与设计不得把提醒挂到计划块上。
- **多提醒的同步**：SPEC 3.2 规则 10 以 `reminder_tag_attachment_v1` capability 门控提醒同步；原型不作为真实网络验证对象，Flutter 阶段按该契约实现。
