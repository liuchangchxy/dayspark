# 接续：待办这一半要重做（顶层设计）

> 本文是新对话的**唯一入口**。读完它 + 指向的材料，就够开工，不需要任何其他背景。

## 一句话目标

**把 DaySpark 的「待办」做到好用的程度（标杆是 Todo清单），并让待办与日历打通。**

## 为什么（现状与痛点）

- 项目早期本想整体复刻 Todo清单，后来自己加了很多需求 → **功能堆了不少，但最基本的待办体验没做好**
- 现在的结构是两块：日历 / 待办。**两个池子互不相通**——
  一条待办就算写了 `dueDate`，**日历上也看不见它**（已查证：`lib/ui/widgets/calendar/` 下零处引用待办；日历只读 `eventsDao`）
- 于是同一件事要么写两遍，要么只写一半

## 这一步要产出什么

**一个顶层设计方案**：待办和日历怎么打通。选一条路，说清理由，再谈落地。

## 三条候选方案

| | 做法 | 代价 |
|---|---|---|
| **A 显示层合并** | 存储不动。日历查询时把带 `dueDate` 的待办一起拉进来画 | 改动最小。但用户写的时候仍要分清"建待办还是建日程" |
| **B 单一对象** | 只存一种记录，**日期只是个字段**。有日期自己上日历，没日期进待办箱，用户永远不用选 | 最接近 Todo清单 的手感。要改表、改同步 DTO、改 ICS 映射 |
| **C 一个入口 + 系统判断** | 一个输入框：带时间段的（`14:00-15:00`）建日程，否则建待办 | 不动存储。但系统要猜、会猜错，条目类型还会跳 |

**A 是"看得见"，B 才是"不用想"。** 用户要的手感偏向 B。

## 硬约束（动手前必须知道）

- **`SPEC.md` 有 8 条冻结需求**，其中「日历 + 待办双一等公民」**会被方案 B 撞上**。B 不是技术问题，是要不要改一条自己拍过板的规矩的问题
- **同步协议是自有的**：2026-09-22 已删除自研 CalDAV 层（`DECISIONS.md`），改走自托管 Dart 服务端 + `packages/dayspark_contracts`。**所以数据模型可以改**，不受 CalDAV 约束
- **ICS 导入导出保留着**（`lib/domain/services/ical/`），模型改动会波及它
- **`CalendarViewMode { day, week, month }`**：日/周视图有时间轴，所以"带日期的待办要不要占时间块"这个问题**必须回答**（Todo清单 只有月视图，它不用回答；它的画法是**全天条，不占时段**）
