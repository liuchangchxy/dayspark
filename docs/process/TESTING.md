# 工程规范与防退化（Regression）防线守则 (TESTING.md)

本项目为保证 Vibe Coding 过程中的系统稳定与需求准确对齐，杜绝“代码改来改去、修复了 A 破坏了 B”的现象，全体开发与 AI 协作必须严格遵守以下工程红线：

> **结构说明**：§一 为**全类型项目通用门禁**（共 10 条），任何项目无条件遵守；§二 为**按需能力门禁**，仅在项目形态命中适用边界时激活，未命中自动豁免（严禁强行套用无关框架规则）；§三 为收敛交付标准 (DoD)；§四 为常用命令。

---

## 一、通用工程门禁（Engineering Gates - 全类型项目通用）

### 1. 缺陷即测试（Defect-Driven Testing）
* **原则**：任何被确认的 Bug 或需求调整，**严禁直接修改业务代码**。
* **标准流程**：
  1. **先定位根因**——禁止猜测式修复。动手前先说清它为什么失败；对着症状下刀，必然要修第二次。
  2. **先写失败测试**：在测试套件中编写针对该 Bug 或新规则的测试用例；
  3. **验证必报错**：确保该测试在现有代码下**必定红灯报错**；
  4. **修改业务代码**：调整实现逻辑，直至该测试变绿；
  5. **终身防退化**：**该测试用例永久保留**，纳入日常全量自动化回归跑道。

### 2. 防测试篡改物理铁律 (Anti-Test Tampering Gate)
* **原则**：测试失败时修业务代码，**严禁为了造绿反向篡改既有测试的断言预期 (assert/expect/toBe)**！严禁删除旧用例、注释断言或标注跳过。
* **物理防线**：
  - 运行 `python tool/guard_test_tampering.py` 自动分析 Git Diff；
  - 任何针对既有测试文件断言行的随意删除或放宽，直接视为质量事故拦截阻断。
* **豁免**：确系合法的需求变更时，必须在提交说明中显式注明，并在 `DECISIONS.md` 中记录，不得静默篡改。

### 3. 禁止硬编码物理绝对路径 (No Hardcoded Paths Gate)
* **原则**：代码严禁与特定开发机的盘符或家目录绑定（如特定用户的本地目录）。
* **物理防线**：
  - 运行 `python tool/scan_hardcoded_paths.py` 扫描源码；
  - 必须使用相对当前文件位置的动态推导（如 `Path(__file__).resolve().parent` / `import.meta.url` 等各语言原生写法）或环境变量注入，保障跨机器与 CI 环境的可移植性。

### 4. 契约防线与禁止静默容错（Contract & Fail-Fast）
* **原则**：拒绝“宽松容错导致的静默死锁或数据漂移”。宁可显式失败，也不要静默吞掉不一致。
* **契约断言**：前后端字段、配置键名、函数返回结构必须通过测试强校验对齐（参见 `REVIEWING.md` 配方 5「跨端键一致性」）。
* **适用**：存在跨进程/跨端契约（API、配置键、原生桥、双端读取）的项目；单一进程内的纯函数库可豁免。

### 5. 1 变 4 根因发散与全局排查法则 (1-to-4 Bug Divergence Protocol)
* **原则**：排查并修复缺陷时，严禁头痛医头只改孤立单行。
* **动手前先 census**：任何“按清单改 N 处”的任务，动手前先全仓重扫一遍同类项，审计抽样结论默认视为下限（如报告说 15 处，实际可能 35 处），不经 census 直接开改视为假完成。
* **发散动作**：针对每个确认的缺陷，必须强制排查 4 类共生问题并输出结论与证据：
  1. **横向同类实现**：全仓搜索同类调用、相似结构、相同 API 模式；
  2. **逆向与边界输入**：空值 / 超长 / 特殊字符 / 并发竞争 / 异步未决 / 网络抖动；
  3. **契约与状态脱节**：字段命名与类型对齐、多语言 / 时区穿透、错误码结构化；
  4. **生命周期与持久化**：缓存失效、本地脏数据、刷新还原、跨用户或注销后残留。

### 6. 规范即测试（Style-as-Test 源码自扫描守卫）
* **原则**：凡是“以后还会有人犯”的代码规范，必须写成一条**终身测试**去扫描自己的源码，让规范从建议变门禁。（`EXECUTION.md` 的“CI grep 版本号”只是本方法的一个特例。）
* **三件套**：
  1. 扫描对象是**源码文本**而非运行行为（如禁止的 API、非法字面量、必须成对出现的键名）；
  2. 守卫**自带违规/合规样本自证**——先证明它能红能绿，再信任它的全仓结论；
  3. 豁免走**白名单**且必须写 WHY；白名单匹配用**内容签名**而非行号（行号一改就漂移）。
* **CLI 约定**：每条守卫都提供 `--selftest`，只跑自带样本并报告成败。红色实证由此变成任何人都能跑（含 CI）的动作，而不是报告里的一句声明。
* **何时用**：同一规范**第二次**被违反时，就值得写成守卫，而不是第三次再修。

### 7. 门禁即证据（新增门禁必须自带一次红色实证）
* **原则**：**一条没红过的门禁视为不存在。** 每新增一条门禁（守卫测试、冒烟断言、CI 步骤），交付时必须附一次“变异实证”：怎么把它打坏的 + 红的原文输出 + 还原后变绿。
* **红色控制必须署名**：文档里每个“已验证”必须指名是**哪条控制**验证的；引用错层（实际死在前一层却写成后一层拦下的）按证据链缺陷处理。
* **为什么**：绿只能证明“这次没炸”，红才能证明“炸了会响”。没经过变异实证的门禁，99% 是“不可能失败的仪式”（见 `REVIEWING.md` 配方 3）。

### 8. 正交验证（Orthogonal Verification）
* **原则**：**验证**一件事的手段，必须独立于**做**这件事的手段。自我确认不算验证。
* **三条常设实例**：
  1. 写代码的人不独自验证——换一双眼睛，或换一个全新会话的 AI，亲手重跑门禁；
  2. 验证清单来自**需求原文**，绝不来自从原文派生出的 todo 列表（todo 会原样继承实现者的误解）；
  3. CI 配置变更先用普通 push 验证，验证通过后才打发布 tag。
* **为什么**：当产物和它的验收出自同一个脑子，一个共同的误解会同时通过两边。只有独立性才拦得住。

### 9. 溯源验收（按原文，不按 todo）
* **原则**：每个用户诉求都要建立 **原文 → todo → 代码** 的可追踪链路，链路本身就是交付物，不是文书工作。
* **验收判据**：判断一件事是否完成，依据是**原文**，不是 todo 列表。todo 是对用户原话的有损压缩；对着它验收，最多只能证明"你做了你写下的"，证明不了"你做了被要求的"。
* **物理形态**：原文逐字进入需求追踪矩阵或变更日志。摘要可以并列，不能替代。

### 10. 测试层级与证据报告（层级不得互相冒充）
* **原则**：测试层级必须**按项目实际边界选择**，低层证据不得冒充更高层的用户链路验收。
* **层级阶梯**（按需取用，未命中即豁免；项目没有对应形态时不需要为了形式制造该层）：
  1. **单元/领域测试**：验证纯逻辑和数据规则；
  2. **API/集成测试**：验证真实服务边界或组件协作；
  3. **数据库/文件物理测试**：验证真实落盘、事务、回滚和转换结果；
  4. **真实客户端 E2E**：仅在存在对应用户界面与流程时启用；
  5. **构建/部署冒烟**：验证交付物能启动或完成关键部署步骤；
  6. **视觉冒烟**：仅在存在可视界面时启用；机器判“是不是白屏”，人眼/AI 评“好不好看”——后者机器测不了。
* **报告纪律**：每次阶段报告必须分别写出**命令、pass、fail、skipped 和未运行原因**，可直接套用 [测试证据模板](docs/qa/TEST_EVIDENCE_TEMPLATE.md)；需求完成状态同步到 [需求追踪矩阵](docs/ROADMAP.md)。
* **禁止**：把构建成功或 Mock 测试称为“真实用户链路通过”。项目没有浏览器时不需要为了形式制造浏览器 E2E；但涉及持久化、外部副作用或关键数据流时，必须运行对应的真实链路验证。

### 11. 凭证卫生（Secret Hygiene Gate）
* **原则**：凭证不是“提交后再删”，而是**从不进入**版本库；历史一旦记录即视为已泄露。
* **入库前**：任何新增/修改的文件若含凭据，必须改为环境变量读取，并在**缺失时明确失败**（禁止用弱口令或示例值兜底）。禁止提交含真实值的 `.env`；只提交 `.env.example`，且其中的值必须是**显眼的占位符**。
* **推送前**：执行脱敏 census（内网地址与主机名、真实口令、API Key、数据库与构建产物），逐项处置并记录。**先 census 再动手。** 项目若公开，此步骤是发布门的一部分。
* **发现已泄露时**：按 `AGENTS.md` 避坑清单第 21 条（历史即公开面）改写历史，而不是补一个删除提交——后者只改变 HEAD，不改变攻击者的可见范围。改写后须在报告中说明 SHA 已变化。
* **为什么**：凭证的泄露面是**全部历史 + 全部克隆**，不是当前工作树。

### 12. 双层自动化物理门禁（CI Gates）
* **本地门禁（Pre-Commit Hook）**：位于 `.git/hooks/pre-commit`。每次在执行 `git commit` 前自动运行全量测试与防篡改、绝对路径检查，未全绿则本地直接拒绝提交。**严禁使用 `git commit --no-verify` 绕过。**
* **远端门禁（GitHub Actions CI）**：位于 `.github/workflows/ci.yml`。每次向主分支推送或提交 PR 时，在干净 runner 环境上自动执行全量测试，红灯严禁合入。
* **发布门必须与 CI 门同构**：凡卡正确性的检查，CI 流水线与发布流水线（`release.yml` 或等价物）的对应 job 必须**双挂**。只挂 CI 不挂发布 = 缺陷从发布链路原样流出。发布门失败的副作用（如 tag 已推但产物未生成）必须在发布文档里写明处置方式。

---

### 13. 漂移守卫（同一事实多处复制）
* **原则**：凡是需要人手工同步到多个文件的事实——版本号、schema id、端口、默认值——**必然漂移**。指定**唯一一个**文件为真理源，其余每一份副本都设门禁比对。
* **同时写明"刻意不设防的项"及原因。** 没写明的省略，看起来和忘记设防一模一样。（读发布 API 的动态徽章、只链接真理源而不复制的文件，都不需要门禁——但要说出来。）
* **与发布联动**：同一守卫带 `--tag` 模式，使与真理源不符的 tag 卡住发布，而不只是卡住 CI。

### 14. 棘轮基线（只许收紧的存量债务）
* **原则**：新立的规范在一份成熟代码库里到处被违反时，**不要因此放弃门禁**——把当前违规项记进基线文件，改为**给数量设门禁**。
* **行为**：新增一处违规立即失败；消掉一处必须同步更新基线，于是数量单调不增。存量债务变得可见、可追踪，而不是把规则整体挡在门外。
* **为什么**：选择从来不是"完美门禁 vs 没有门禁"。棘轮把全有或全无的规则变成单向阀，这才是它能在真实代码上落地的原因。
* **退场**：基线清空时，删掉基线文件，门禁转入零容忍。

## 二、按需能力门禁（Capability-Gated - 根据项目类型触发）

以下规则根据项目形态按需激活，**非适用项目自动豁免**，严禁强行套用无关框架规则：

### 1. 全双语字典对齐与无硬编码文案门禁（适用于包含人机交互/文案的项目）
* **适用边界**：包含用户界面（Web/GUI/App）、CLI 命令行交互输出或后端 API 错误码响应的项目。纯底层算法库或驱动自动豁免。
* **核心原则**：
  - **零硬编码自然语言**：展示文案统一通过语言字典管理，严禁在业务逻辑中散落硬编码文本；
  - **后端/API 纯净度**：接口错误统一返回结构化错误码，严禁拼接自然语言句子；
  - **字典键双向对齐 (Key Parity)**：主语言与目标语言字典键集必须 100% 镜像对齐，漏译物理报错；
  - **静态扫描守卫**：按 §一.6「规范即测试」写一条源码扫描测试，拦截新写的裸文案；
  - **堵住全部五个返工源**：封闭类型配方、门禁组合、伪语言与出口清单配方见 `LOCALIZATION.md` 第二部分。只有门禁没有类型层是自觉；只有类型层没有冒烟层，通知和小组件会漏一辈子。

### 2. 界面主题与端侧预算门禁（适用于包含图形界面 GUI/Web/移动端的项目）
* **适用边界**：仅当项目包含图形视图（Web/桌面端/移动端）时生效，纯 CLI/后端自动豁免。
* **核心原则**：
  - **语义化 Design Tokens**：颜色通过语义变量定义，日夜模式自动响应，禁止组件裸写固定色值；
  - **防闪烁 (Zero FOUC)**：入口必须配置早期主题检测，杜绝渲染前白屏闪烁；
  - **外设特化剔除律**：移动端/触屏/受限视口中，严禁残留桌面特化的交互提示（如键盘快捷键指南、鼠标悬浮浮层提示、不可点击的快捷键徽章等）；无外设支撑的交互元素必须显式剔除或转为触控交互；
  - **平台感知**：任何 UI / 交互改动，必须**显式**考虑所有目标平台的差异（桌面鼠标 vs 移动触摸、悬浮 vs 长按、键盘 vs 手势），绝不在一个平台上验证完就假定其余平台没问题。只在一个平台上验证过的改动，视为未验证。
  - **受限视口物理预算**：移动端顶栏高度必须严格约束在单行（建议 ≤ 44px），严禁标题、状态、操作按钮折行撑高侵占视口空间；核心触发源与当前状态即时反馈必须在首屏内零滚动可见，禁止以“允许页面上下滚动”替代视口信息密度的工程治理。

### 3. 异步与偶发失败排查（按需启用）
* **适用边界**：**仅当**测试涉及异步界面、浏览器时序、网络或偶发失败时启用；**不要把这套流程强加给普通确定性单元测试**。
1. **保留失败现场**：记录命令、运行次数、失败步骤和测试顺序；按场景补充当前页面/状态、关键 DOM 或运行时状态、控制台/运行日志、失败请求、服务端日志、网络状态及服务启动方式。
2. **先复现并缩小范围，再改实现**：尽量在相同条件下复现，将长流程缩成最小复现；先判断问题属于产品逻辑、异步就绪/等待条件、测试间状态污染、旧构建产物，还是环境/服务进程问题。
3. **等待可观察条件**：等待页面或业务状态达到预期，并设置合理上限。固定 `sleep`、无差别加长超时、全局自动重试或放宽断言**不能作为首选修复**；测试必须保留原本要验证的行为约束。
4. **确认测到的是当前代码**：核对测试实际启动的服务和前端资源。若测试服务提供的是构建产物，先构建并确认加载的是本次构建结果；每个场景应有明确前置状态和清理，避免前序失败污染后续场景。
5. **按风险重复验证**：修复后先跑最小复现和相关回归。只有已确认存在偶发性或竞态风险时，才安排重复采样；**固定复现次数不是通用 DoD**。报告实际条件、总运行次数及通过/失败数，不以一次成功掩盖已知不稳定性。

## 三、收敛交付标准 (Definition of Done - DoD)

为防止“无限对抗审查导致精神内耗、修不彻底”，确立科学的交付收敛判定准则：

1. **Bug 严重度台阶分级**：
   - **P0 致命级**：数据丢失损坏、主流程死锁崩溃 ➔ **必须彻底清零，一票否决**；
   - **P1 严重级**：核心业务功能与 SPEC 不符、乱码、关键流程失败 ➔ **必须彻底修复**；
   - **P2 次要级**：极端网络抖动容错、文案微调 ➔ **记入待办，不阻断交付**；
   - **P3 洁癖级**：理论假想风险、微小代码格式 ➔ **直接忽略，严禁内耗**。
2. **交付绿灯条件**：
   - 所有 P0 / P1 问题已清零；
   - 所有本次声明为适用范围的自动化测试与静态扫描（硬编码路径、断言防篡改）100% 通过；
   - 自动化测试套件 `skipped=0`（若因缺少外部物理硬件跳过，必须如实声明豁免原因）；
   - 达到上述条件即可果断确认验收通过并上线交付！

## 四、常用工程检验与本地运行命令

```bash
# 1. 全量测试（DaySpark 权威命令）
flutter test

# 2. 静态分析（必须零 issue）
dart analyze .

# 3. 防测试篡改：扫 git diff 里被删除/放宽的既有断言
python3 tool/guard_test_tampering.py

# 4. 硬编码绝对路径扫描（只扫 git 跟踪的文件）
python3 tool/scan_hardcoded_paths.py

# 5. 行尾空格 / 换行符混用（CI 门禁，不进 pre-commit）
python3 tool/check_whitespace.py
```

不要把构建成功或 Mock 测试称为真实用户链路通过。涉及持久化、外部副作用或关键数据流时，必须运行对应的真实链路验证。
