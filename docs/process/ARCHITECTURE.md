# 顶层架构推导法 (ARCHITECTURE.md)

> **定位**：本文件教**方法**——如何从零推出一份优秀的架构设计；推导的**产物**写进 `SPEC.md` 第 2 节（系统架构与数据流转）。SPEC 第 2 节是“这个项目长什么样”，本文是“怎么想出它该长这样”。
> 适用对象： vibecoding 开发者——你不需要会画 UML，需要会回答下面七个问题。

---

## 七步推导（严格按序，前一步不落纸不进下一步）

1. **先写“力”，不先画图**
   架构 = 约束下的取舍。先列：给谁用 / 多大规模 / 几人维护 / 什么绝对不能丢。
   → 这四行直接淘汰 90% 的技术选项（个人工具不配集群，单人维护不配微服务）。

2. **数据模型先行——先定“名词”**
   定义核心实体、它们的平等关系与不变式（谁能改谁、什么必须同时成立）。
   → 系统的坚固程度 ≈ 实体与不变式的清晰程度；界面、API、同步都只是这个模型的投影。**这一步定错了，后面全是返工。**

3. **划“一致性边界”**
   标出哪里必须原子（事务内），哪里允许暂时不一致、靠什么收敛（队列/游标/重试）。
   → 这是后端的灵魂问题；“单写入路径”这类黄金纪律往往就是这条边界的产物。

4. **选“无聊的技术”——规模决定技术，不是品味**
   每引入一个组件都问：我的规模配得上它吗？能用文件解决的不上数据库，能用单机的不上分布式。
   → “没用高级货”通常是判断正确，不是落后。

5. **接口先于实现——先冻结“接线图”**
   先写数据结构与接口契约（前后端/模块间共用的那份），再写实现。
   → 契约冻结后各方才能并行、才能互相验收，而不是互相踩。

6. **为删除而设计**
   自问：半年后想拆掉某块，能不能干净地切下来？（依赖单向、逻辑圈定在目录内、测试能自动告诉你伤了什么）
   → 好架构的隐藏标准：**删除成本低**。

7. **决策留痕 + 验证架构是一体的**
   关键取舍当场记入 `DECISIONS.md`（背景/决策/影响）；设计里必须包含**验收方式**（e2e 矩阵、契约测试），验证不是写完代码后补的，是设计的一部分。

---

## “好架构”的三判据（忘掉“优雅/先进”这类空词）

> **改起来便宜 · 用起来难错 · 坏了能看见**

- 改起来便宜：分层清晰、契约冻结、删除干净；
- 用起来难错：默认拒绝/单写入口/类型与约定在类型系统或测试里强制，而非靠自觉；
- 坏了能看见：错误上浮有通道、派生状态有统一失效机制、监控/日志在设计里而不是补丁。

交付前用这三句各打一次分，比任何架构图都诚实。

---

## “抄 / 造”判据（防止重复造轮子与盲从）

| 层 | 策略 |
|----|------|
| **商品层**（框架、数据库、通用 UI、工具库） | **用现成的开源**，不自研 |
| **规范层**（HTTP/OAuth/协议类） | **照抄公开 RFC/标准**，标准就是全世界共用的轮子 |
| **差异层**（你的核心数据模型 + 独有体验） | **必须自己写**——它是产品本身 |

调研候选项目时的纪律见 AGENTS 避坑清单（务实调研、代码级实证、拒绝 Star 数教条）：**抄的是“决策与标准”，不是整仓代码；整仓 fork 前先查它的协议兼容与许可证。**
