# 对抗性审查配方 (REVIEWING.md)

> **定位**：审查 = **发现期**。修复期必须回到 `TESTING.md` 铁律“根因全局治理（RCA）”——发现一处，修复时全局清扫同类，严禁孤立改单行。
> 输出纪律：审查者**必须亲手重跑门禁**（analyze/test），禁止只读实现者的报告就下结论；diff 范围之外发现的问题标注“⚠️ 范围外”，交上级裁决，不许自行扩权修改。

---

## 输出格式（双裁决，缺一不可）

1. **规格符合**：逐条对照 brief/SPEC → ✅ / ❌（附证据 file:line）
2. **质量结论**：`Approved` 或按 **P0–P3** 分级的发现清单（Critical→P0/P1、Important→P1、Minor→P2/P3，映射见 EXECUTION §0）
每条发现必须带：`文件:行号` + “错在哪” + “为什么要紧”；禁止“改得好一点”式空话。

---

## 五种攻击配方（每轮审查逐条过）

### 1. 空转测试识别
测试断言无实质约束即为“空转”。查法：删掉被测实现/替换为恒等实现，测试是否仍绿？断言是否只在复读实现（如 `expect(f(x), f(x))`）？**测试必须能在实现错误时变红，才算存在。**

### 2. 边界与量化数学
对时间、金额、索引、序列号亲手算边界：`±1`、空集合、零长度、进位/跨日、浮点精度地板。**例**：SQL 用浮点日期比较、Dart 用微秒整数比较，两侧在同一边界可能分歧——必须用同一规范形式（如定宽字符串）或补边界测试钉死。

### 3. 证据链倒挂检测（“不可能失败的门禁”）
问：**这个验收门在实现错误时能不能红？** 若门禁依赖的文件根本没被构建引用（配置写了没接线）、或验证与被验证物无关 → 门禁是**空转的仪式**。多层取证：配置文件 → 构建设置 → 产物二进制，三层都见才算“生效”。

### 4. 自证向量陷阱
测试用**与实现相同的公式**计算期望值 = 循环自证，实现改坏也全绿。必须钉**外部字面值**（标准组织发布的测试向量、已知手算答案、上游 golden 文件）。

### 5. 跨端键一致性
同一契约被多处实现时（前后端字段、双端原生读取、配置键），全仓 grep 新旧键名，核对 **key-for-key + 类型一致 + 版本门**；任何一端漏改/类型不符 = 静默数据丢失。

---

## 审查者三律

1. **门禁亲手跑**：报告里的绿不算数，自己跑一遍再下结论；
2. **红要能复现**：宣称修好的关键缺陷，优先“还原前的红 → 修复后的绿”实证，而非只看新测试绿；
3. **对抗姿态**：每轮审查至少主动尝试一次“如何让这套实现出错”（换公式、塞畸形输入、并发、跨端不一致），找不到洞也要写明找过哪里。
